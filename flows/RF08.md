# Fluxos funcionais do RF08 — Consulta de status dos pedidos

**RF08 — O sistema deve disponibilizar consulta de status dos pedidos.**

Este arquivo descreve o comportamento da consulta independentemente da arquitetura. As quatro abordagens devem preservar a mesma entrada, ordem de validação, estados, erros e resposta HTTP.

## Relação com o RF05 e o RF06

O RF05 cria o pedido como `PENDING`. O consumidor financeiro de `OrderCreated` cria o pagamento e altera o pedido para `PAYMENT_PENDING`. No RF06, o consumidor de pedidos processa o resultado do pagamento e altera o pedido para `PAID` ou `CANCELED`.

O RF08 consulta o status persistido em `orders`, sem executar essas transições. Não exige a existência de um registro em `order_payments`: um pedido recém-criado já pode ser consultado.

## Estados do pedido

Reutilizar o enum `OrderStatus` existente. A representação HTTP é numérica.

| Membro | Valor | Significado |
| ------ | ----- | ----------- |
| `OrderStatus.PENDING` | `0` | Pedido criado, aguardando preparação financeira |
| `OrderStatus.PAYMENT_PENDING` | `1` | Pedido aguardando atualização decorrente do pagamento |
| `OrderStatus.PAID` | `2` | Pedido pago |
| `OrderStatus.CANCELED` | `3` | Pedido cancelado |

O código utiliza os membros do enum, sem números mágicos. A consulta não cria novos estados, tabelas ou campos.

## `GET /orders/:orderId/status`

Consulta o status atual de um único pedido pelo seu identificador.

### Autenticação e entrada

O middleware `authenticate` é registrado na própria rota. O header `x-api-key` deve ser igual à variável de ambiente `X_API_KEY`, sem fallback. Header ausente ou incorreto gera `ForbiddenError` (`403`) antes de validar o identificador ou consultar dados.

`orderId` é o UUID do pedido, recebido no path. A operação não requer body nem parâmetros de query.

Exemplo:

```http
GET /orders/0f5ead3a-8c1e-4b2a-9d4c-1a2b3c4d5e6f/status
x-api-key: <X_API_KEY>
```

### Fluxo da rota

1. Autenticar a requisição.
2. Obter `orderId` a partir do path.
3. Validar o formato UUID de `orderId`, seguindo a mesma validação utilizada no RF06.
4. Se o identificador for inválido:
   - gerar `InvalidOrderIdError`;
   - retornar HTTP `400` com `error`, `message` e `statusCode`;
   - interromper o fluxo antes de consultar dados.
5. Consultar o pedido pelo identificador informado.
6. Se o pedido não existir:
   - gerar `OrderNotFoundError`;
   - retornar HTTP `404` com `error`, `message` e `statusCode`.
7. Obter o status persistido no pedido.
8. Transformar o identificador e o status para a representação HTTP.
9. Retornar HTTP `200` com `orderId` e `status`.

### Regras da operação

- Todos os estados de `OrderStatus` podem ser consultados, inclusive `PENDING` e `CANCELED`.
- O status retornado pertence ao pedido, não ao pagamento. Os enums possuem significados e valores distintos.
- A leitura não altera pedido, pagamento, itens ou estoque e não publica eventos.
- Não executar o simulador de pagamento, iniciar consumers ou aguardar o consumo de eventos durante a requisição.
- A consulta não necessita de bloqueio de escrita.
- Atualizações dos consumers são assíncronas. Após a criação, a consulta pode retornar `PENDING` até a preparação financeira. Após o processamento do pagamento, pode retornar `PAYMENT_PENDING` até o consumo do evento de aprovação ou recusa.
- Retornar o estado persistido no momento da leitura, sem deduzir um estado a partir de `order_payments`. Consultas posteriores podem observar a atualização feita pelo consumidor.
- Um pedido cancelado é um resultado válido de consulta e retorna `200`, sem gerar `PaymentDeclinedError`.

### Resposta de sucesso

HTTP `200 OK`:

```json
{
  "orderId": "0f5ead3a-8c1e-4b2a-9d4c-1a2b3c4d5e6f",
  "status": 2
}
```

Neste exemplo, `status` corresponde a `OrderStatus.PAID`. O payload contém somente o identificador e o status do pedido.

### Exceções HTTP

Todas as respostas de erro possuem `error`, `message` e `statusCode`. Reutilizar as classes existentes.

| Condição | Classe | HTTP | Mensagem |
| -------- | ------ | ---- | -------- |
| API key ausente ou incorreta | `ForbiddenError` | `403` | `Forbidden` |
| UUID inválido | `InvalidOrderIdError` | `400` | `Invalid order id: {orderId}` |
| Pedido inexistente | `OrderNotFoundError` | `404` | `Order not found: {orderId}` |

Exemplo de pedido inexistente:

```json
{
  "error": "OrderNotFoundError",
  "message": "Order not found: 0f5ead3a-8c1e-4b2a-9d4c-1a2b3c4d5e6f",
  "statusCode": 404
}
```

### Fluxo de sucesso

```text
requisição com orderId
  → autenticação
  → validação do UUID
  → consulta do pedido
  → leitura do status persistido
  → representação HTTP com orderId e status
  → resposta 200
```

### Fluxos de exceção

```text
API key ausente ou incorreta → ForbiddenError → resposta 403
UUID inválido → InvalidOrderIdError → resposta 400
UUID válido + pedido inexistente → OrderNotFoundError → resposta 404
```

## Cenários de teste

- Consulta de pedido em cada estado: `PENDING`, `PAYMENT_PENDING`, `PAID` e `CANCELED`, com resposta `200` e status numérico correspondente.
- Pedido recém-criado, ainda sem pagamento, retornando `PENDING`.
- Pagamento aprovado ou recusado, com evento ainda não consumido, retornando o status `PAYMENT_PENDING` persistido no pedido.
- Nova consulta após o consumo de `PaymentApproved` retornando `PAID`; após o consumo de `PaymentDeclinedError`, retornando `CANCELED`.
- Consultas repetidas preservando os dados e sem publicar eventos.
- UUID inválido retornando `InvalidOrderIdError` (`400`) antes de consultas.
- UUID válido sem pedido correspondente retornando `OrderNotFoundError` (`404`).
- API key ausente ou incorreta retornando `ForbiddenError` (`403`), inclusive quando o UUID também for inválido.

Na implementação, os testes de integração compartilhados da rota pertencem a `test/integration/orders/`, em arquivo próprio por operação, com autenticação em arquivo transversal. Usar prefabs para dados no PostgreSQL e helpers para HTTP autenticado. Nos cenários com consumers, publicar eventos reais no Redis e aguardar seus efeitos observáveis antes da consulta final.

Os testes unitários respeitam a unidade de negócio de cada abordagem: use cases na Clean e na Domain; handler de rota no MVC; função de negócio da rota no monólito. O contrato em `test/contracts/order.md` e o Swagger em `docs/openapi.yaml` devem documentar o mesmo comportamento quando a rota for implementada.

# Fluxos funcionais do RF05 — Criação de pedido

Este arquivo descreve o comportamento funcional da rota de criação de pedido independentemente da arquitetura utilizada. Os projetos podem distribuir as responsabilidades entre rotas, controllers, models, use cases ou repositories de maneiras diferentes, mas devem preservar a mesma ordem de validação, o mesmo fluxo de dados, as mesmas exceções, o mesmo evento e a mesma resposta HTTP.

## Modelo de dados

O pedido é persistido nas tabelas `Order` e `OrderItem`. O processamento financeiro do evento `OrderCreated` cria o registro correspondente em `OrderPayment`.

```text
Order
-----------------------
Id
IdUser
Status
Total
DataCadastro

OrderItem
-----------------------
Id
IdOrder
IdProduct
Quantity
PriceUnit

OrderPayment
-----------------------
IdOrder
Status
PaymentDetails
PaidAt
CreatedAt
```

Cada `OrderItem` pertence a um `Order` por meio de `IdOrder`. `PriceUnit` registra o preço do produto no momento da criação do pedido, de forma que alterações posteriores no preço do produto não modifiquem o valor do pedido já criado. `Total` corresponde à soma de `Quantity × PriceUnit` de todos os itens. `DataCadastro` corresponde a `createdAt` na representação HTTP.

Os status são numéricos e representados por enums na aplicação: `OrderStatus.PENDING = 0`, `OrderStatus.PAYMENT_PENDING = 1` e `OrderPaymentStatus.PENDING = 0`.

Cada `OrderPayment` pertence a exatamente um `Order`. `IdOrder` é simultaneamente chave primária e chave estrangeira para `Order`, garantindo a relação 1:1 e impedindo mais de um pagamento para o mesmo pedido. `Status` é criado como `PENDING` (`0`). `PaymentDetails` e `PaidAt` permanecem nulos até o pagamento ser realizado. `CreatedAt` registra a criação do pagamento.

## Comportamento comum

A rota de pedidos segue inicialmente este fluxo:

1. Receber a requisição HTTP.
2. Validar o header `x-api-key` comparando-o com a variável de ambiente `X_API_KEY`.
3. Se o header estiver ausente ou tiver um valor diferente:
   - gerar `ForbiddenError`;
   - retornar HTTP `403` com `error`, `message` e `statusCode`;
   - interromper o fluxo antes de executar consultas, alterações ou publicar eventos.
4. Se a autenticação for válida, continuar o fluxo específico da rota.

## `POST /orders`

Cria um novo pedido a partir de um usuário e de uma lista de produtos com suas respectivas quantidades.

### Entrada

```json
{
  "userId": 10,
  "items": [
    {
      "productId": 1,
      "quantity": 2
    },
    {
      "productId": 5,
      "quantity": 1
    }
  ]
}
```

### Fluxo

1. Obter `userId` e `items` a partir do body.
2. Validar que `items` seja uma lista não vazia.
3. Se `items` estiver ausente, não for uma lista ou estiver vazio:
   - gerar `EmptyOrderItemsError`;
   - retornar HTTP `400` com `error`, `message` e `statusCode`;
   - não consultar nem persistir dados e não publicar o evento.
4. Validar a `quantity` de cada item antes de executar consultas.
5. Cada quantidade é válida somente quando for um número inteiro maior que zero.
6. Se alguma `quantity` estiver ausente, for não numérica, fracionária, igual a zero ou negativa:
   - gerar `InvalidQuantityError` com o valor recebido;
   - retornar HTTP `400` com `error`, `message` e `statusCode`;
   - não consultar nem persistir dados e não publicar o evento.
7. Consultar o usuário correspondente a `userId`.
8. Se o usuário não existir:
   - gerar `UserNotFoundError` com o identificador recebido;
   - retornar HTTP `404` com `error`, `message` e `statusCode`;
   - não criar o pedido e não publicar o evento.
9. Consultar todos os produtos informados em `items`.
10. Se algum produto não existir:
    - gerar `ProductNotFoundError` com o identificador recebido;
    - retornar HTTP `404` com `error`, `message` e `statusCode`;
    - não criar o pedido e não publicar o evento.
11. Comparar a quantidade solicitada de cada produto com seu estoque atual. Se um produto aparecer mais de uma vez, considerar a soma das quantidades solicitadas para esse produto.
12. Se a quantidade total solicitada de algum produto for maior que seu estoque disponível:
    - gerar `InsufficientStockError`;
    - retornar HTTP `409` com `error`, `message` e `statusCode`;
    - não criar o pedido e não publicar o evento.
13. Gerar um identificador para o pedido, definir `Status` como `PENDING` e registrar `DataCadastro`.
14. Criar o `Order` associado ao usuário.
15. Criar os `OrderItems` associados ao pedido, registrando em `PriceUnit` o preço atual de cada produto.
16. Calcular `Total` pela soma de `Quantity × PriceUnit` de todos os itens e registrá-lo no pedido.
17. Persistir o pedido e todos os seus itens como uma única operação atômica.
18. Publicar o evento `OrderCreated` somente após a persistência bem-sucedida.
19. Transformar o pedido e seus itens para a representação HTTP.
20. Retornar HTTP `201` com o pedido criado.

### Regras da operação

- Todas as validações devem ser concluídas antes da criação do pedido.
- O pedido é criado inicialmente com o status `PENDING`.
- O valor unitário salvo em cada item é o preço atual do produto no momento da criação.
- O valor total é calculado no servidor; um total eventualmente enviado pelo cliente deve ser ignorado.
- A criação do pedido não decrementa o estoque diretamente. A reserva ou baixa pode ser realizada posteriormente pelo módulo de estoque ao consumir o evento `OrderCreated`.
- A persistência do pedido e dos itens é atômica: uma falha não pode deixar um pedido incompleto ou itens sem o respectivo pedido.
- Nenhum evento deve ser publicado quando uma validação falhar ou a persistência não for concluída.

### Evento `OrderCreated`

Após a criação bem-sucedida, deve ser publicado um evento com o identificador do pedido, o usuário e os itens solicitados:

```json
{
  "event": "OrderCreated",
  "orderId": 123,
  "userId": 10,
  "items": [
    {
      "productId": 1,
      "quantity": 2
    },
    {
      "productId": 5,
      "quantity": 1
    }
  ]
}
```

O evento pode ser consumido pelo módulo responsável pelo estoque, pelo pagamento ou por outras ações decorrentes da criação do pedido.

### Consumo financeiro de `OrderCreated`

O consumidor financeiro processa `OrderCreated` de forma transacional e idempotente. Todas as consultas e alterações no PostgreSQL pertencem à mesma transação. Um payload inválido gera `InvalidOrderCreatedPayloadError`, classe derivada de `InvalidPayloadError`, e segue o fluxo de Dead Letter descrito em [RedisConsumer](RedisConsumer.md).

1. Receber o evento e converter seu conteúdo para um `OrderCreatedPayload` válido.
2. Procurar o `Order` correspondente a `orderId`, mantendo bloqueio de escrita sobre o pedido durante a transação.
3. Se o pedido não existir:
   - gerar `OrderNotFoundError`;
   - desfazer a transação;
   - não executar `XACK`.
4. Procurar `OrderPayment` pelo mesmo `orderId`.
5. Se o pagamento já existir, considerar o processamento idempotente:
   - não criar outro pagamento;
   - não alterar novamente o pedido;
   - concluir a transação com sucesso.
6. Se o pagamento não existir:
   - criar `OrderPayment` com `Status` igual a `PENDING`;
   - registrar `PaymentDetails` e `PaidAt` como nulos;
   - registrar `CreatedAt`;
   - alterar o status do pedido de `PENDING` para `PAYMENT_PENDING`;
   - confirmar todas as alterações na mesma transação.
7. Executar `XACK` somente depois que a transação for confirmada com sucesso.

`order_payments.order_id` é chave primária e chave estrangeira para `orders.id`. Essa restrição no banco garante que processamentos concorrentes não criem dois pagamentos para o mesmo pedido; a consulta anterior à inserção, isoladamente, não oferece essa garantia.

```text
OrderCreated válido
  → transação
  → bloqueio e consulta do pedido
  → pedido inexistente: OrderNotFoundError, rollback e sem XACK
  → consulta do pagamento
  → pagamento existente: nenhuma alteração, commit e XACK
  → pagamento inexistente: cria OrderPayment PENDING
  → altera Order para PAYMENT_PENDING
  → commit
  → XACK
```

### Resposta de sucesso

HTTP `201 Created`:

```json
{
  "id": 123,
  "userId": 10,
  "status": 0,
  "total": 250.00,
  "createdAt": "2026-09-19T18:30:00Z",
  "items": [
    {
      "productId": 1,
      "quantity": 2,
      "unitPrice": 100.00
    },
    {
      "productId": 5,
      "quantity": 1,
      "unitPrice": 50.00
    }
  ]
}
```

`createdAt` é representado em ISO-8601 UTC e `items` é sempre um array não vazio nessa operação.

### Fluxo de sucesso

```text
userId + items
  → validação da lista e das quantidades
  → consulta do usuário
  → consulta dos produtos
  → validação do estoque
  → criação do pedido com status PENDING
  → criação dos itens com os preços atuais
  → cálculo e registro do total
  → persistência atômica
  → publicação de OrderCreated
  → representação HTTP
  → resposta 201
```

### Fluxos de exceção

```text
lista de itens ausente, inválida ou vazia
  → EmptyOrderItemsError
  → resposta 400
```

```text
quantity inválida
  → InvalidQuantityError
  → resposta 400
```

```text
entrada válida + usuário não encontrado
  → UserNotFoundError
  → resposta 404
```

```text
usuário encontrado + produto não encontrado
  → ProductNotFoundError
  → resposta 404
```

```text
usuário e produtos encontrados + estoque insuficiente
  → InsufficientStockError
  → resposta 409
```

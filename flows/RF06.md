# Fluxos funcionais do RF06 — Processamento de pagamento

**RF06 — O sistema deve processar pagamentos dos pedidos.**

O pagamento é simulado, sem cobrança real ou provedor externo. As quatro abordagens preservam a mesma entrada, ordem de validação, modelagem, eventos, erros e respostas HTTP. A variável do experimento continua sendo a organização das responsabilidades.

## Relação com o RF05

O RF05 cria o pedido com `OrderStatus.PENDING`. O consumidor financeiro de `OrderCreated` cria o respectivo `OrderPayment` com status `PENDING` e altera o pedido para `PAYMENT_PENDING` em uma transação.

O RF06 processa esse pagamento e publica o resultado. O `OrderConsumer` consome `PaymentApproved` para marcar o pedido como pago ou `PaymentDeclinedError` para cancelá-lo. A rota registra o resultado do pagamento; o consumidor atualiza o pedido de forma assíncrona.

## Modelo de dados e enums

Utilizar as tabelas `orders` e `order_payments` existentes. `order_payments.order_id` continua sendo chave primária e estrangeira para `orders.id`, garantindo um pagamento por pedido.

| Enum                 | Membro            | Valor | Significado                                     |
| -------------------- | ----------------- | ----- | ----------------------------------------------- |
| `OrderStatus`        | `PENDING`         | `0`   | Pedido criado, aguardando preparação financeira |
| `OrderStatus`        | `PAYMENT_PENDING` | `1`   | Pedido aguardando pagamento                     |
| `OrderStatus`        | `PAID`            | `2`   | Pedido pago                                     |
| `OrderStatus`        | `CANCELED`        | `3`   | Pedido cancelado por recusa                     |
| `OrderPaymentStatus` | `PENDING`         | `0`   | Pagamento pendente                              |
| `OrderPaymentStatus` | `PAID`            | `1`   | Pagamento aprovado                              |
| `OrderPaymentStatus` | `DECLINED`        | `2`   | Pagamento recusado                              |

O código utiliza os membros dos enums. A representação HTTP dos status é numérica. Os tokens e o provedor simulado também possuem enums: `PaymentToken.APPROVED`, `PaymentToken.DECLINED` e `PaymentProvider.SIMULATED`.

Na aprovação ou recusa, `paymentDetails` registra `provider: simulated`, `transactionId` UUID e `amount`. `paidAt` recebe a data atual somente na aprovação; na recusa definitiva, permanece nulo. `createdAt` conserva o instante de criação do pagamento pelo RF05.

### Segunda chance após recusa de pagamento

Cada pedido admite até duas tentativas de pagamento. `order_payments.attempts` conta as tentativas já registradas (0, 1 ou 2); `order_payment_attempts` persiste cada tentativa individualmente (`order_id`, `attempt_number`, `idempotency_key`, `payment_token`, `status`, `payment_details`, `paid_at`, `created_at`), com `(order_id, idempotency_key)` e `(order_id, attempt_number)` únicos.

Uma aprovação, em qualquer tentativa, é definitiva: `OrderPayment.status = PAID`, publica `PaymentApproved`. Uma recusa na **primeira** tentativa não é definitiva: a resposta HTTP é `422`, mas `OrderPayment.status` permanece `PENDING`, nenhum evento é publicado e o pedido continua `PAYMENT_PENDING` com o estoque ainda reservado — uma segunda tentativa, com outra chave de idempotência, pode ocorrer. Uma recusa na **segunda** tentativa é definitiva: `OrderPayment.status = DECLINED`, publica `PaymentDeclinedError`. Uma compra só exige outro pedido depois da recusa definitiva (segunda tentativa) ou de uma aprovação já ter esgotado o propósito do pagamento.

## `POST /orders/:orderId/payment`

Processa o pagamento simulado de um pedido, persiste seu resultado e publica o evento correspondente após o commit.

### Autenticação e entrada

O middleware `authenticate` é registrado na própria rota. O header `x-api-key` deve ser igual a `X_API_KEY`, sem fallback. Header ausente ou incorreto gera `ForbiddenError` (`403`) antes de consultar dados ou publicar eventos.

`orderId` é o UUID do pedido, recebido no path. O header `Idempotency-Key` é obrigatório e deve ser um UUID válido: identifica esta tentativa de pagamento dentro do pedido. Ausente ou inválido gera `InvalidIdempotencyKeyError` (`400`), antes de consultas. O body contém:

```json
{
  "paymentToken": "sim-approved"
}
```

| Token          | Resultado |
| -------------- | --------- |
| `sim-approved` | Aprovação |
| `sim-declined` | Recusa    |

A comparação é exata. Campo ausente, nulo, vazio, de outro tipo ou com qualquer outro valor é inválido. Não receber dados de cartão. O valor utilizado é o total já persistido no pedido; ignorar um valor eventualmente enviado pelo cliente.

### Fluxo da rota

1. Autenticar a requisição.
2. Validar o formato UUID de `orderId`. Identificador inválido gera `InvalidOrderIdError` (`400`), antes de consultas.
3. Validar o formato UUID de `Idempotency-Key`. Ausente ou inválido gera `InvalidIdempotencyKeyError` (`400`), antes de consultas.
4. Validar o token. Token inválido gera `InvalidPaymentTokenError` (`400`), antes de consultas.
5. Na transação, consultar o pedido com bloqueio de escrita até o commit ou rollback. Pedido inexistente gera `OrderNotFoundError` (`404`).
6. Consultar o pagamento pelo mesmo `orderId`. Registro ainda não criado pelo consumidor financeiro gera `PaymentNotReadyError` (`409`). O cliente pode tentar novamente após a preparação do RF05.
7. Consultar uma tentativa já persistida para este pedido com esta `Idempotency-Key`:
   - se existir e o `paymentToken` enviado for igual ao registrado, retornar o resultado original dessa tentativa (`200` ou `422`), sem simular de novo, sem alterar dados e sem publicar outro evento — mesmo que o pedido já tenha avançado de estado;
   - se existir com um `paymentToken` diferente, retornar `PaymentAttemptConflictError` (`409`).
8. Para uma chave nova (um novo processamento), exigir pagamento `PENDING`, pedido `PAYMENT_PENDING` e menos de duas tentativas já registradas para o pedido. Qualquer combinação diferente gera `InvalidOrderPaymentStateError` (`409`) — inclusive uma chave nova depois do pagamento alcançar `PAID` ou `DECLINED`, mesmo enquanto o `OrderConsumer` ainda não processou esse resultado.
9. Executar a simulação pelo token e pelo total persistido do pedido, sem aleatoriedade na decisão.
10. Gerar `transactionId` UUID e registrar os detalhes da tentativa. Persistir a tentativa em `order_payment_attempts` (número da tentativa, chave, token, resultado, `paymentDetails`, `paidAt`) e incrementar `order_payments.attempts`.
11. Decidir o efeito sobre `order_payments` e sobre a publicação:
    - **aprovação, em qualquer tentativa**: persistir o pagamento como `PAID` com `paidAt`; é definitiva;
    - **recusa na primeira tentativa** (a tentativa que acabou de ser registrada é a 1ª e não aprovada): **não** alterar `order_payments.status` (permanece `PENDING`); não é definitiva; habilita uma segunda tentativa;
    - **recusa na segunda tentativa**: persistir o pagamento como `DECLINED` com `paidAt` nulo; é definitiva.
12. Confirmar a transação.
13. Somente quando o resultado desta tentativa for definitivo (aprovação, ou recusa que esgota as duas tentativas), publicar `PaymentApproved` ou `PaymentDeclinedError` no stream `payments`, após o commit. Uma primeira recusa não publica evento.
14. Depois da publicação (quando houver), responder `200` com o pagamento aprovado ou `422` com o erro de recusa — da tentativa atual, definitiva ou não.

Uma recusa é um resultado persistido por tentativa. Preparar a resposta `422` durante a operação e enviá-la após o commit e a publicação (quando houver). Lançar uma exceção que provoque rollback dentro da transação apagaria esse resultado.

Na Clean e na Domain, a transação HTTP vive no `RouterBase` + `DbManager`. O use case solicita publicação pela abstração de eventos; a implementação registra o efeito após commit. O controller retorna `RouteResponse` para que a resposta seja enviada após a transação e os callbacks.

### Idempotência e concorrência

O bloqueio de escrita no pedido serializa solicitações simultâneas e é compatível com o bloqueio usado pelo consumidor financeiro do RF05. Para uma dada `Idempotency-Key`, somente o primeiro processamento grava a tentativa, atualiza o pagamento quando aplicável e publica um evento quando definitivo; a repetição dessa mesma chave com o mesmo token retorna o resultado original gravado para ela, mesmo após o pedido avançar de estado por uma tentativa posterior. A mesma chave com um token diferente é um conflito (`PaymentAttemptConflictError`), não uma repetição. Uma chave nova está sujeita ao limite de duas tentativas por pedido: a terceira chave nova (ou qualquer chave nova após um resultado definitivo) é rejeitada com `InvalidOrderPaymentStateError`, inclusive enquanto o consumidor ainda processa esse resultado.

Preservar `transactionId`, `paymentDetails` e `paidAt` de cada tentativa, e o `createdAt` do pagamento, nas repetições. Falhas de autenticação, validação ou falhas antes de persistir o resultado da tentativa não publicam eventos de pagamento nem consomem uma das duas tentativas. A operação não altera estoque; a primeira recusa preserva o estoque reservado por não encerrar o pedido.

### Resposta de aprovação

HTTP `200 OK`:

```json
{
  "orderId": "0f5ead3a-8c1e-4b2a-9d4c-1a2b3c4d5e6f",
  "status": 1,
  "paymentDetails": {
    "provider": "simulated",
    "transactionId": "da16e5ce-82c4-441b-bd19-3ec6e6e2d4a1",
    "amount": 250
  },
  "paidAt": "2026-10-14T00:30:00.000Z",
  "createdAt": "2026-10-14T00:29:00.000Z"
}
```

`status` representa o pagamento. A resposta não inclui o status do pedido, atualizado de forma assíncrona. Datas são serializadas em ISO-8601 UTC.

### Exceções HTTP

Todas as respostas possuem `error`, `message` e `statusCode`.

| Condição                                     | Classe                          | HTTP  | Mensagem                                     |
| --------------------------------------------- | -------------------------------- | ----- | --------------------------------------------- |
| API key ausente ou incorreta                  | `ForbiddenError`                 | `403` | `Forbidden`                                   |
| UUID de pedido inválido                       | `InvalidOrderIdError`            | `400` | `Invalid order id: {orderId}`                 |
| `Idempotency-Key` ausente ou inválida         | `InvalidIdempotencyKeyError`     | `400` | `Invalid idempotency key`                     |
| Token inválido                                | `InvalidPaymentTokenError`       | `400` | `Invalid payment token`                       |
| Pedido inexistente                            | `OrderNotFoundError`             | `404` | `Order not found: {orderId}`                  |
| Pagamento ainda não criado                    | `PaymentNotReadyError`           | `409` | `Payment not ready for order: {orderId}`      |
| Mesma chave com token diferente do registrado | `PaymentAttemptConflictError`    | `409` | `Payment attempt conflict for order: {orderId}` |
| Chave nova fora das tentativas permitidas     | `InvalidOrderPaymentStateError`  | `409` | `Invalid payment state for order: {orderId}`  |
| Pagamento recusado (1ª ou 2ª tentativa)       | `PaymentDeclinedError`           | `422` | `Payment declined for order: {orderId}`       |

Exemplo de recusa:

```json
{
  "error": "PaymentDeclinedError",
  "message": "Payment declined for order: 0f5ead3a-8c1e-4b2a-9d4c-1a2b3c4d5e6f",
  "statusCode": 422
}
```

## Eventos de resultado

Os tipos `PaymentApproved` e `PaymentDeclinedError` pertencem a `EventType`; o stream `payments` é centralizado em `EventStream.Payments`. Cada evento possui classe concreta e classe de payload com conversão e validação, seguindo o padrão de `OrderCreated`.

O envelope contém `event`, `eventId` UUID, `timestamp` UTC e `payload`. No Redis, seguir a serialização existente, com payload em JSON. O token não é incluído no evento. `transactionId` corresponde ao valor persistido no pagamento.

### `PaymentApproved`

```json
{
  "event": "PaymentApproved",
  "eventId": "c049cce2-29f6-4c89-b3a1-3fe67501a928",
  "timestamp": "2026-10-14T00:30:00.000Z",
  "payload": {
    "orderId": "0f5ead3a-8c1e-4b2a-9d4c-1a2b3c4d5e6f",
    "transactionId": "da16e5ce-82c4-441b-bd19-3ec6e6e2d4a1",
    "amount": 250,
    "paidAt": "2026-10-14T00:30:00.000Z"
  }
}
```

Seu consumo altera o pedido para `OrderStatus.PAID`.

### `PaymentDeclinedError`

```json
{
  "event": "PaymentDeclinedError",
  "eventId": "a3bddc60-dfd6-46fd-9a90-deb324517bda",
  "timestamp": "2026-10-14T00:30:00.000Z",
  "payload": {
    "orderId": "0f5ead3a-8c1e-4b2a-9d4c-1a2b3c4d5e6f",
    "transactionId": "da16e5ce-82c4-441b-bd19-3ec6e6e2d4a1",
    "amount": 250
  }
}
```

Seu consumo devolve as quantidades dos itens persistidos ao estoque e altera o pedido para `OrderStatus.CANCELED` na mesma transação. O evento e a exceção HTTP de mesmo nome são representações distintas: a classe do evento é `PaymentDeclinedErrorEvent`, enquanto o tipo serializado permanece `PaymentDeclinedError`.

### Publicação após commit

Uma falha na publicação não desfaz o pagamento persistido. Sem outbox, uma falha entre commit e publicação pode manter o pedido em `PAYMENT_PENDING` apesar de o pagamento já ter resultado definitivo. A repetição da rota não republica o evento e não resolve essa janela. Uma garantia de recuperação exige evolução específica do mecanismo, fora deste recorte.

Uma primeira recusa não publica evento algum: nada fica pendente de publicação para ela. Só a tentativa que produz o resultado definitivo (aprovação, ou segunda recusa) está sujeita a essa janela.

## Consumo pelo setor de pedidos

O `OrderConsumer` observa o stream `payments` em seu próprio consumer group, configurado com o prefixo obrigatório `ORDER_CONSUMER_`. Seu ciclo de vida é separado de HTTP: `orderConsumerApp.ts` compõe o consumidor, e `server.ts` o inicia e encerra junto ao consumidor financeiro.

1. Converter e validar o payload. `orderId` e `transactionId` devem ser UUIDs válidos; `amount` deve ser número finito não negativo. `PaymentApproved` exige também `paidAt` ISO-8601 UTC válido, inclusive a data do calendário.
2. Payload inválido gera `InvalidPaymentApprovedPayloadError` ou `InvalidPaymentDeclinedPayloadError`, derivados de `InvalidPayloadError`, seguindo Dead Letter conforme [RedisConsumer](RedisConsumer.md).
3. Abrir transação e consultar o pedido com bloqueio de escrita.
4. Pedido inexistente gera `OrderNotFoundError`: rollback e sem `XACK`.
5. Determinar o destino: `PAID` para aprovação e `CANCELED` para recusa.
6. Pedido já no destino: concluir sem alterações, tratando a reentrega de forma idempotente.
7. Pedido em `PAYMENT_PENDING`: na recusa, carregar os itens persistidos, agregar por produto e bloquear os produtos em ordem crescente de ID, incluindo excluídos logicamente. Devolver as quantidades sem reativar produtos excluídos; alterar o pedido para `CANCELED` na mesma transação. Produto inexistente gera `ProductNotFoundError`, rollback e retry. Na aprovação, alterar somente o pedido para `PAID`, mantendo o estoque.
8. Qualquer outro status gera `InvalidOrderPaymentStateError`: rollback, sem sobrescrever o estado e seguindo retry.
9. Confirmar a transação e somente depois executar `XACK`.

Na aprovação, o consumidor altera somente o pedido. Na recusa, altera pedido e estoque atomicamente; o estado `CANCELED` protege contra dupla devolução em reentregas, inclusive concorrentes. O consumidor não altera o pagamento. Logs, retry e Dead Letter seguem o algoritmo existente. Na Clean e na Domain, handlers abrem transação via `DbManager` e passam os dados necessários aos use cases.

### Organização por arquitetura

- Monólito: `consumers/consumerOrder.ts` copia o algoritmo completo do financeiro, alterando configurações, despacho e handlers que usam TypeORM diretamente.
- MVC: `OrderConsumer` herda da base existente, nomeada `RedisConsumer`, e mantém os handlers no próprio consumidor, usando models para persistência. `ConsumerFinancial` utiliza a mesma base.
- Clean: `OrderConsumer` compõe `Consumer`, registra handlers separados de aprovação e recusa e chama os use cases `ApproveOrderPayment` e `CancelOrderPayment`.
- Domain: `ordering/order.consumer.ts` registra handlers das operações `ordering/approveOrderPayment` e `ordering/cancelOrderPayment`. A rota pertence a `payments/processOrderPayment`, registrada em `payments/payment.controller.ts`. A integração entre contextos ocorre pelos eventos compartilhados.

## Cenários de teste

- Aprovação e recusa definitiva com persistência dos detalhes e publicação do evento correspondente após commit.
- Primeira recusa retornando `422`, sem alterar `order_payments.status`, sem publicar evento e preservando o pedido `PAYMENT_PENDING` e o estoque reservado.
- Segunda chance: recusa seguida de aprovação (pedido concluído, sem devolução de estoque) e recusa seguida de recusa (pedido cancelado, evento publicado uma única vez).
- Valor do cliente ignorado em favor do total persistido.
- Pedido permanecendo pendente até o consumo do evento definitivo.
- Atualização para `PAID` ou `CANCELED` pelo consumidor e `XACK` após commit.
- Repetição da mesma `Idempotency-Key` com o mesmo token, antes e depois de uma tentativa posterior ter resolvido o pagamento, preservando o resultado daquela tentativa e sem nova publicação.
- Mesma `Idempotency-Key` com um token diferente retornando `PaymentAttemptConflictError`, sem persistir nem publicar.
- Uma chave nova após o resultado definitivo (aprovação ou segunda recusa) retornando `InvalidOrderPaymentStateError`, inclusive enquanto o consumidor ainda processa esse resultado.
- Solicitações concorrentes respeitando o limite de duas tentativas, com um único resultado e uma única publicação por tentativa definitiva.
- Reentrega de eventos idempotente, inclusive concorrente, sem dupla devolução de estoque.
- Aprovação mantém a baixa; recusa definitiva devolve os itens persistidos, incluindo produtos excluídos logicamente, sem reativá-los.
- Identificador, chave de idempotência e token inválidos; pedido inexistente, pagamento ainda indisponível e estados incompatíveis.
- Preparação pelo consumidor financeiro permitindo posterior processamento do pagamento.
- API key ausente ou incorreta.
- Payload inválido em Dead Letter; pedido inexistente e status incompatível no consumo seguindo retry.
- Erros de validação (UUID, chave, token) e falhas antes de persistir o resultado da tentativa não consomem uma das duas tentativas nem publicam evento.

Unitários devem manter os mesmos dados e cenários nas quatro abordagens, com dependências próprias mockadas. Dados mockados de `payment-approved`, `payment-declined` e `process-order-payment` ficam em arquivos próprios em `test/mocks/`. Helpers HTTP e asserts ficam fora dessa pasta.

Integrações compartilhadas ficam separadas por operação. Para consumers, publicar eventos reais no Redis e aguardar os efeitos no PostgreSQL e a confirmação no Redis. O contrato de pedidos e o Swagger documentam o mesmo comportamento.
